## Map详解

Map与HashMap

## 一、 宏观视角：接口与实现的关系

首先，我们要纠正一个知觉误区：**Map 是接口，HashMap 是落地。**

- **Map 接口**：定义了 Key-Value 映射的抽象行为。它在 Java 集合框架中是独立的一支（不继承 Collection）。
- **HashMap**：是 Map 最主流的实现。它的核心命题是：**如何利用 Hash 算法实现 O(1) 级别的查找效率？**

## 二、 深度解构 HashMap

在 Java 8 之后，HashMap 经历了一次优化。

如果不显式指定初始容量，HashMap 的默认初始容量是 **16**。

- **源码定义**：`static final int DEFAULT_INITIAL_CAPACITY = 1 << 4; // 16`
- **为什么要 16？** 这是一个折中的选择。太小（比如 4）会导致刚存几个数就频繁扩容；太大（比如 128）则会浪费内存，因为每个桶位都是一个引用。
  - 更重要的是，16 是 **2 的幂次方**，配合位运算 `(n - 1) & hash` 能让数据分布得非常均匀。

### 1. 数据结构的演进：从 链表 到 树化

Java 7 的 HashMap 是**数组 + 单向链表**。当 Hash 冲突严重时，链表过长，查询性能会退化到 O(n)。

Java 8 引入了**红黑树**：

- **触发条件**：当桶（bucket）中的链表长度 > 8 且数组总长度 >= 64 时，链表转为红黑树。
- **退化条件**：当扩容或删除元素导致树节点数 <= 6 时，红黑树退回到链表。

> **问题：为什么是 8 和 6？**
>
> 这是根据**泊松分布**计算的概率学选择。在负载因子为 0.75 的情况下，连续 8 个元素落入同一个桶的概率极低（约千万分之六）。选择 6 是为了留出缓冲空间，防止在 8 附近反复插入删除导致频繁的树化/退化，造成性能抖动。

### 2. 扩容机制（Resize）的艺术

HashMap 默认初始容量是 16，负载因子是 0.75。

- **计算位运算**：容量必须是 2^n。为什么？因为计算下标时使用 `(n - 1) & hash`，当 n 是 2 的幂次时，这等同于取模，但位运算性能极高。
- **Java 8 的扩容优化**：不再需要重新计算每个元素的哈希值。因为容量翻倍，元素的位置要么在**原位置**，要么在**原位置 + 旧容量**的位置。通过 `(e.hash & oldCap) == 0` 即可快速拆分。

### 3. 并发下的“死穴”

- **Java 7**：多线程扩容由于使用“头插法”，会导致**环形链表**，从而 CPU 100%。
- **Java 8**：改用“尾插法”，解决了死循环问题，但依然**线程不安全**。在并发下会出现数据覆盖、Size 不准等问题。

> **高级建议**：“在追求高性能并发时，我会优先考虑 `ConcurrentHashMap`，它在 Java 8 利用 CAS + `synchronized` 锁桶节点，比传统的 `Hashtable` 性能高出几个量级。”



### 3. tableSizeFor方法

在 Java 8 的 `HashMap` 源码中，`tableSizeFor` 的作用是：**给定一个容量请求 `cap`，返回一个大于或等于 `cap` 的最小的 2 的幂次方。**

比如：输入 `10`，返回 `16`；输入 `25`，返回 `32`；输入 `64`，返回 `64`。



为什么 HashMap 的数组长度 n 必须是 2^k？（减少冲突；提高效率）

- **性能优化**：计算下标通常用取模 `%`，但位运算 `(n - 1) & hash` 的效率极高。只有当 n 是 2 的幂次方时，这两者才完全等价。
- **均匀分布**：2^n - 1 的二进制全为 `1`（如 15 是 `1111`），这能保证散列后的索引分布更均匀，减少 Hash 冲突。

```java
    /**
     * Returns a power of two size for the given target capacity.
     */
    static final int tableSizeFor(int cap) {
        int n = cap - 1;
        n |= n >>> 1;
        n |= n >>> 2;
        n |= n >>> 4;
        n |= n >>> 8;
        n |= n >>> 16;
        return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
    }

```

#### 第一步：为什么要 `n = cap - 1`？

这是为了防止 `cap` **本身就是 2 的幂次方**的情况。如果没有这一步，输入 `8` 经过后面的位移操作会变成 `15`，最后 `+1` 变成 `16`。这就平白无故翻了一倍。

#### 第二步：核心位移操作（铺满 1）

这段代码的核心逻辑是：**利用最高位的 1，把后面所有的位都填成 1。**

假设我们输入 `n = 10`（二进制为 `0000 1010`）：

1. `n |= n >>> 1`：
   - `0000 1010` (原码)
   - `0000 0101` (右移1位)
   - 结果：`0000 1111`（此时最高位及其后 1 位都成了 1）
2. `n |= n >>> 2`：
   - `0000 1111`
   - `0000 0011` (右移2位)
   - 结果：`0000 1111`（最高位及其后 3 位都成了 1）
3. **接力下去**：以此类推，通过 `1, 2, 4, 8, 16` 的位移，由于 `int` 类型是 32 位的，这一套组合拳下来，**只要最高位有一个 1，它后面所有的位都会变成 1。**

#### 第三步：收尾 `n + 1`

当所有的位都变成了 `1`（比如 `0000 1111`，十进制是 `15`），最后执行 `n + 1`，它一定会进位变成 `0001 0000`（十进制 `16`）



> Q:**如果我传入一个负数或者 0，这个方法会返回什么？**

- **回答**：
  - 如果 `cap` 是 `0`，执行 `n = -1`，由于 `-1` 在计算机里补码全为 `1`，后续位移不变。最后三元运算符判断 `n < 0`，返回 `1`。
  - 如果 `cap` 是负数，同理，返回 `1`。
  - 这保证了 HashMap 的容量永远是一个合法的正整数。

### 4. transient

它的 `table` 数组（存储数据的核心阵列）竟然是用 `transient` 修饰的： `transient Node<K,V>[] table;`

**Q：既然 table 不序列化，那 HashMap 的数据是怎么存下来的？**

- **深度回答**：因为 HashMap 重写了 `writeObject` 和 `readObject` 方法。
- **原因**：由于 `hash` 值依赖于 JVM 具体的实现和哈希算法，直接序列化整个物理数组是非常低效且不可靠的（不同版本的 JDK 扩容机制或 Hash 算法可能略有差异）。
- **策略**：HashMap 选择了**手动序列化**。它只序列化 `size` 和每一个键值对（Entry），反序列化时再重新计算 Hash 并填充到新的 `table` 中。这叫**逻辑序列化**，比物理序列化更健壮、更节省空间。

### 5. resize 方法

`resize` 不仅仅是简单的“扩容”，它承担了**初始化和 重哈希 两大职责\****

#### 5.1 扩容的“导火索”：Threshold。首先要明确什么时候触发 `resize`：

当 `HashMap.size > threshold`（当前元素个数超过阈值）时，调用 `resize`。

> threshold = capacity * loadFactor
>
> 默认情况下，即 16 * 0.75 = 12。

------

#### 5.2. Java 8 的核心优化：不再重算 Hash

在 Java 7 中，扩容是一场灾难。每一个元素都要重新调用 `hash()` 方法，再根据新容量取模。

**Java 8 巧妙地利用了 2^n 容量的特性：**

当数组容量翻倍（比如从 16 变 32），元素的新位置只有两种可能：

1. **原位置**（Index）
2. **原位置 + 旧容量**（Index + oldCap）

**背后的数学逻辑**：

扩容后，掩码 `n - 1` 的最高位多了一个 `1`。我们只需要判断元素的 `hash` 值在这一位上是 `0` 还是 `1`。

- 如果是 `0`：位置不变。
- 如果是 `1`：位置移动 `oldCap`。

> 源码中使用 `(e.hash & oldCap) == 0` 来判断。这种位运算直接避开了繁琐的取模和重哈希，效率极高。

------

#### 5.3. 扩容过程的“保姆级”拆解

你可以把 `resize` 想象成一次**搬家工程**：

#### 第一阶段：计算新容量

- 如果旧容量已经达到最大值（2^{30}），则不再扩容，直接把阈值设为 `Integer.MAX_VALUE`。
- 否则，新容量 = 旧容量 * 2，新阈值 = 旧阈值 * 2。

#### 第二阶段：创建新数组

根据新容量 `newCap` 创建一个新的 `Node<K,V>[] newTab`。

#### 第三阶段：数据迁移（最重要的部分）

遍历旧数组的每一个桶（Bucket）：

1. **普通节点**：直接搬到新数组的新位置。
2. **红黑树节点**：调用 `split` 方法。如果拆分后树的大小 <= 6，则退化回链表。
3. **链表节点**：
   - Java 8 维护了**两组链表**：`loHead/loTail`（低位链表，原位置）和 `hiHead/hiTail`（高位链表，原位置 + oldCap）。
   - 遍历原链表，根据 `(e.hash & oldCap) == 0` 把节点分别挂在两个链表下。
   - **最后一步**：把这两组链表整体搬移到新数组。这避免了 Java 7 中单节点频繁移动导致的“头插法循环死锁”问题，Java 8 采用的是**尾插法**，保持了原有的顺序。

### 6. 头插法/尾插法

1. 头插法：新来的节点总是作为链表的第一个节点，原来的头节点接在新节点的后面。

- *逻辑*：`newNode.next = table[i]; table[i] = newNode;`
- *初衷*：设计者认为“后进入的数据被访问的概率更高”（类似缓存的局部性原理），且操作简单。

2. 尾插法：新来的节点挂在链表的末尾。

- *逻辑*：遍历链表找到最后一个节点，`lastNode.next = newNode;`

#### **核心一：扩容操作**

这是导致问题的根源：

- **头插法（逆序）**：在扩容迁移数据时，旧链表中的元素被一个个取出来，重新通过头插法放入新数组。这会导致**链表的顺序发生翻转**。
  - 比如旧链表是 `A -> B -> C`，扩容后可能变成 `C -> B -> A`。
- **尾插法（顺序）**：Java 8 引入了高低位链表，迁移时保持了元素的**原始先后顺序**。
  - 旧链表是 `A -> B -> C`，迁移后依然是 `A -> B -> C`（或者部分被移走，但相对顺序不变）。

#### 核心二：死循环

在 **JDK 7** 中，多线程并发执行 `resize` 时：

1. 线程 A 准备扩容，读取到链表 `A -> B`，它记录了 `e = A, next = B`。
2. 此时线程 A 被挂起，线程 B 进场，快速完成了整个扩容过程。因为是头插法，链表顺序反转成了 `B -> A`。
3. 线程 A 恢复执行，它认为 `A` 后面跟着 `B`。它先把 `A` 放入新桶，然后去处理 `B`。
4. 当处理 `B` 时，发现 `B` 的 `next` 竟然指向了 `A`（这是线程 B 刚才改的）。
5. 于是，线程 A 又把 `A` 挂在了 `B` 后面。
6. 一个环形链表 `A <-> B` 诞生了。下次调用 `get()` 如果落在这个桶，CPU 会瞬间飙升到 100%。

**JDK 8 的改进**： 因为改用了**尾插法**，迁移前后顺序一致。`A` 永远在 `B` 前面，或者它们被分到了不同的桶，**绝不会出现 `B.next = A` 的情况**，从而彻底解决了扩容死循环问题。



## 三、 HashMap vs 其他 Map 家族成员

map的不同实现：

| **实现类**            | **核心特性**                                                | **适用场景**                        |
| --------------------- | ----------------------------------------------------------- | ----------------------------------- |
| **LinkedHashMap**     | 维护了一个双向链表，记录插入顺序或访问顺序。                | 实现 **LRU Cache** 的首选。         |
| **TreeMap**           | 基于红黑树实现，Key 必须实现 Comparable 或传入 Comparator。 | 需要按 Key **自然排序**或范围检索。 |
| **ConcurrentHashMap** | 线程安全，分段思想（Java 8 为行级锁）。                     | 高并发环境。                        |

## 四、 避坑指南与实战建议

1. **关于 `hashCode()` 和 `equals()`**：

   这是老生常谈但必错的点。如果你重写了 `equals` 没重写 `hashCode`，HashMap 会认为两个逻辑相等的对象是不同的，导致数据丢失或重复。

2. **Key 的不可变性**：

   推荐用 `String` 或 `Integer` 作为 Key。如果用一个自定义对象，且在放入 Map 后修改了参与 Hash 计算的属性，那么这个对象就丢了——再也无法通过 `get()` 找到它。

3. **初始化容量预估**：

   如果你知道要存 100 个元素，不要直接 `new HashMap(100)`。因为 100 / 0.75 = 133.3。为了避免扩容抖动，建议初始容量设为 2^8 = 256 或者利用 Guava 的工具类。



## ConcurrentHashMap

Q:KEY/VALUE都不允许为空，为什么？

A:为了消除两种语义。在单线程 HashMap 中，可以用 `containsKey` 判断；但在并发下，如果 `get(key)` 返回 `null`，无法确定是"值本身就是 null"还是"在判断的过程中值被删除了"

## 一、 ConcurrentHashMap：从“分段锁”到“行级锁”的进化

在 Java 8 中，CHM 抛弃了 Java 7 那套厚重的 `Segment`（分段锁）设计，转而采用了更细粒度的控制。

### 1. 核心原理：CAS + synchronized

Java 8 的 CHM 看起来和 HashMap 结构相似（数组+链表+红黑树），但在并发控制上非常精妙：

- **比较并插入CAS (Compare And Swap)**：在插入新节点时，如果桶（Bucket）为空，直接通过 CAS 原子操作放入，**无锁执行**，效率极高。

- **synchronized**：如果桶不为空（即发生了碰撞），则只锁定**当前的头节点（或树的根节点）**。

  > **经验必谈点**：为什么不用 `ReentrantLock`？因为 Java 6 之后 `synchronized` 引入了偏向锁、轻量级锁和锁消除优化（锁升级）。在大量细粒度锁的场景下，`synchronized` 的内存开销比 `ReentrantLock` 更小。

### 2. 扩容

这是 CHM 最牛的地方。当一个线程发现 Map 正在扩容时，它不会坐视不管，而是会**主动参与协助扩容**。

- 它利用 `ForwardingNode`（转发节点）来标记已经处理过的桶。
- 多个线程可以同时搬运不同的桶，极大地缩短了扩容导致的停顿时间。

### 3. 读取的“弱一致性”

CHM 的 `get` 方法是**完全无锁**的。它通过 `volatile` 关键字保证了节点的 `val` 和 `next` 指针的可见性。

> **提醒**：既然无锁，那读到的是最新的吗？答案是：CHM 保证的是**弱一致性**，即它不保证能立刻读到其他线程刚写入的数据，但保证不会读到乱码或破坏结构的数据。



## LinkedHashMap

## 一、 LinkedHashMap：有序性与 LRU

HashMap 是无序的，但如果你需要**按插入顺序**或者**按访问频率**排序，就得靠 LinkedHashMap。

### 1. 底层结构：双向链表 + 散列表

LinkedHashMap 在 HashMap 的基础上，给每个节点（Node）增加了两个属性：`before` 和 `after`。 它维护了一张**贯穿整个散列表的双向循环链表**。

### 2. 如何实现 LRU（最近最少使用）算法？

LRU 的核心逻辑是：**新访问的元素移到末尾，最久未访问的在表头。**

在 LinkedHashMap 中，只需要两步：

1. 构造时设置 `accessOrder = true`。
2. 重写 `removeEldestEntry(Map.Entry eldest)` 方法。

```java
// 这是一个极简的 LRU Cache 实现
public class MyLRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int CACHE_SIZE;

    public MyLRUCache(int size) {
        // true 表示按访问顺序排序，false 表示按插入顺序
        super(size, 0.75f, true);
        this.CACHE_SIZE = size;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        // 当 Map 大小超过设定的容量时，自动删除最老的数据
        return size() > CACHE_SIZE;
    }
}
```
