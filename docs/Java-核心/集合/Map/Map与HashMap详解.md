# Map 与 HashMap 详解

---

## 一、宏观视角：接口与实现的关系

首先，需要明确一个核心概念：**Map 是接口，HashMap 是其具体实现**。

| 组件 | 角色 | 核心职责 |
|------|------|----------|
| **Map 接口** | 抽象层 | 定义 Key-Value 映射的行为契约，是 Java 集合框架中独立的一支（不继承 Collection） |
| **HashMap** | 实现层 | 基于 Hash 算法实现，核心命题是：**如何利用 Hash 算法实现 O(1) 级别的查找效率** |

## 二、深度解构 HashMap

### 2.1 核心参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 初始容量 | 16 (`1 << 4`) | 太小会频繁扩容，太大浪费内存 |
| 负载因子 | 0.75 | 扩容阈值 = 容量 × 负载因子 |
| 树化阈值 | 8 | 链表长度超过 8 且数组长度 ≥ 64 时转为红黑树 |
| 退化阈值 | 6 | 树节点数 ≤ 6 时退化为链表 |

**为什么容量必须是 2 的幂次方？**
- 位运算效率：`(n - 1) & hash` 等价于取模，但位运算性能更高
- 均匀分布：`2^n - 1` 的二进制全为 1，保证散列索引分布均匀

### 2.2 数据结构演进：从链表到红黑树

**Java 7**: 数组 + 单向链表
- 问题：Hash 冲突严重时，查询性能退化到 O(n)

**Java 8**: 数组 + 链表/红黑树
- **树化条件**：桶中链表长度 > 8 **且** 数组长度 ≥ 64
- **退化条件**：树节点数 ≤ 6

> **设计思考：为什么是 8 和 6？**  
> 基于**泊松分布**计算：负载因子 0.75 时，8 个元素落入同一桶的概率仅为千万分之六。选择 6 作为退化阈值是为了防止在 8 附近频繁树化/退化导致的性能抖动。

### 2.3 tableSizeFor 方法解析

该方法的作用是：**给定容量请求 `cap`，返回大于等于 `cap` 的最小 2 的幂次方**。

```java
static final int tableSizeFor(int cap) {
    int n = cap - 1;      // 防止 cap 本身就是 2 的幂次方
    n |= n >>> 1;         // 把最高位的 1 向右扩散 1 位
    n |= n >>> 2;         // 继续扩散 2 位
    n |= n >>> 4;         // 继续扩散 4 位
    n |= n >>> 8;         // 继续扩散 8 位
    n |= n >>> 16;        // 继续扩散 16 位
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}
```

**核心逻辑**：利用位移操作将最高位的 1 扩散到后面所有位，最后 `+1` 得到最小的 2 的幂次方。

### 2.4 扩容机制（Resize）

#### 2.4.1 扩容触发条件
当 `size > threshold`（阈值 = 容量 × 负载因子）时触发扩容。

#### 2.4.2 Java 8 的优化：无需重算 Hash

**数学原理**：容量翻倍时，元素新位置只有两种可能：
- **原位置**：`(e.hash & oldCap) == 0`
- **原位置 + 旧容量**：`(e.hash & oldCap) != 0`

#### 2.4.3 扩容流程（搬家工程）

```
┌─────────────────────────────────────────────────────────────┐
│                    resize() 扩容流程                         │
├─────────────────────────────────────────────────────────────┤
│  第一阶段：计算新容量                                        │
│    └─> 若旧容量已达最大值(2^30)，阈值设为 Integer.MAX_VALUE   │
│    └─> 否则：新容量 = 旧容量 × 2，新阈值 = 旧阈值 × 2        │
│                                                             │
│  第二阶段：创建新数组                                        │
│    └─> Node<K,V>[] newTab = new Node[newCap]               │
│                                                             │
│  第三阶段：数据迁移                                          │
│    └─> 遍历旧数组每个桶                                     │
│         ├─> 普通节点：直接搬移到新位置                       │
│         ├─> 红黑树节点：调用 split()，若节点数≤6则退化       │
│         └─> 链表节点：按高位/低位拆分为两个链表后整体搬移    │
└─────────────────────────────────────────────────────────────┘
```

### 2.5 并发安全性分析

| 版本 | 插入方式 | 并发问题 |
|------|----------|----------|
| Java 7 | 头插法 | 多线程扩容导致**环形链表**，CPU 100% |
| Java 8 | 尾插法 | 解决死循环，但仍**线程不安全**（数据覆盖、Size 不准） |

> **推荐方案**：高并发场景优先使用 `ConcurrentHashMap`，Java 8 中利用 CAS + `synchronized` 锁桶节点，性能远超传统 `Hashtable`。

### 2.6 transient 关键字的作用

`table` 数组使用 `transient` 修饰：
```java
transient Node<K,V>[] table;
```

**原因**：HashMap 重写了 `writeObject` 和 `readObject` 方法，采用**逻辑序列化**策略：
- 只序列化 `size` 和键值对
- 反序列化时重新计算 Hash 并填充
- 避免 Hash 值依赖 JVM 实现导致的序列化不可靠问题

### 2.7 头插法 vs 尾插法

| 特性 | 头插法（Java 7） | 尾插法（Java 8） |
|------|------------------|------------------|
| 插入位置 | 链表头部 | 链表尾部 |
| 扩容后顺序 | 逆序 | 保持原序 |
| 并发问题 | 可能形成环形链表 | 避免死循环 |

## 三、Map 家族成员对比

| 实现类 | 底层结构 | 核心特性 | 适用场景 |
|--------|----------|----------|----------|
| **HashMap** | 数组 + 链表/红黑树 | 无序，O(1) 查找 | 通用场景 |
| **LinkedHashMap** | 数组 + 双向链表 | 保持插入/访问顺序 | LRU 缓存 |
| **TreeMap** | 红黑树 | Key 自然排序，支持范围查询 | 有序场景 |
| **ConcurrentHashMap** | 数组 + 链表/红黑树 | 线程安全，分段锁 | 高并发场景 |

## 四、避坑指南与实战建议

### 4.1 hashCode 与 equals 契约

**必须同时重写**，否则会导致：
- 逻辑相等的对象被视为不同 Key
- 数据丢失或重复

### 4.2 Key 的不可变性

推荐使用 `String` 或 `Integer` 作为 Key。如果使用自定义对象：
- 不要修改参与 Hash 计算的属性
- 否则对象将无法通过 `get()` 找到

### 4.3 初始化容量预估

```java
// 错误：100 个元素会触发扩容
new HashMap(100);  

// 正确：100 / 0.75 ≈ 134，向上取 2 的幂次方
new HashMap(256);  

// 更好：使用 Guava
Maps.newHashMapWithExpectedSize(100);
```

## 五、LinkedHashMap 与 LRU 实现

### 5.1 底层结构

在 HashMap 基础上，每个节点增加 `before` 和 `after` 指针，维护**双向循环链表**。

### 5.2 LRU Cache 实现

```java
public class MyLRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int CACHE_SIZE;

    public MyLRUCache(int size) {
        // accessOrder = true 表示按访问顺序排序
        super(size, 0.75f, true);
        this.CACHE_SIZE = size;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        // 超过容量时自动删除最老元素
        return size() > CACHE_SIZE;
    }
}
```

**LRU 核心逻辑**：
1. `accessOrder = true`：开启访问顺序模式
2. 新访问元素移到链表末尾
3. 超过容量时删除表头（最久未访问）

## 总结

| 核心要点 | 说明 |
|----------|------|
| **容量设计** | 必须是 2 的幂次方，配合位运算实现高效散列 |
| **结构演进** | Java 8 引入红黑树优化极端 Hash 冲突场景 |
| **扩容优化** | 利用位运算避免重算 Hash，提升扩容效率 |
| **线程安全** | HashMap 非线程安全，并发场景用 ConcurrentHashMap |
| **Key 选择** | 推荐不可变类型，必须正确实现 hashCode/equals |
